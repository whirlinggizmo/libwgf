# libwgf roadmap

What is left to build, in order. libwgf is done when it ships three games ([SPEC.md](../SPEC.md), "Done means games"); each milestone leaves everything before it working, and every game stays playable in CI. A finished step is deleted from this file, not ticked off, and its record moves to [HISTORY.md](HISTORY.md) in the same commit. What exists now is [ARCHITECTURE.md](ARCHITECTURE.md).

## Milestone 2: a chase-camera racing game

One track from glTF, a car with real vehicle physics, a chase camera with smoothing, lap timing, a HUD, shadows, and an environment map. It proves 3D rendering, physics, asset streaming, and performance.

The plan, decided before building and reviewed by Rob (HISTORY.md, "Milestone 2's plan" and "Milestone 2's plan, reviewed"). Games test the framework only if they can't bend it (SPEC.md), so:

- **Game code first.** The racer's game-side code is written before the framework under it, in [docs/sketches/racer/](sketches/racer/README.md): the stage, the car's intent, the chase camera, laps, the HUD, the scene file, and the lap autopilot, as the game should be able to write them. Each step below says which part of it the step makes real ("Sketch:"). Where what is built differs from the sketch, the difference is recorded: in [FRICTION.md](FRICTION.md) when the game has to work around it, in HISTORY.md when the sketch was wrong.
- **Two kinds of session.** This one builds the framework: the layers, their tests and examples, and the combination scenes. The racer (`games/racer/`) is built by a separate game-developer session, started by Rob. It works in its own directory from the public API, the docs, and `wgf new` alone, with edits to libwgf denied to it. It files each gap in FRICTION.md, and works around a gap only by logging the workaround there. From step 4 on, each step's framework lands before the game session takes up its part of the sketch, and its friction is triaged (a framework task, or a decision that the workaround is fine) before the next step's framework starts.
- **The game early.** From step 4, a drivable racer exists, and every later step lands in it as well as in its own examples, so the game pushes back on each API while that layer is fresh.

Each step is a few small commits, each reviewed against CONVENTIONS.md, verified, and pushed; each new public call is reached by the feature test, and each new layer's tests are carried with its code.

## Milestone 2.5: jam-ready

libwgf is a framework, not one game's library: a game jam must not have to stop and add a feature under a deadline (SPEC.md, "Done means games", 2.5). After the racer, what was trimmed from wgrender-c and libwgt and no game has brought back is restored (the catalog below, less what milestone 2 carries), each feature with a showcase example in the browser check and the size table, wgrender-c's suite the model; breadth stays cheap, since a program links only what it calls. Outlined here; planned in full once milestone 2 closes.

- **2D drawing:** rounded rectangles and borders, a line thickness and a corner radius on shapes, nine-slice textures, text slices drawn and measured without copying, and clip actors (scrolling regions).
- **Textures:** a settable placeholder.
- **From Asteroids' friction** (FRICTION.md): sounds without files (a sound from samples made in code, and a starter sound in the templates); timers on the tick clock owned by a behavior or the runtime, ended with their owner (`after`, `every`, a cooldown, an actor's blink); an area query (anything on these layers within a radius, no actor needed); named collider layers in the scene format; the UI's default focus when the last input was keys or a pad, and a guard so a press begun before a screen appears doesn't activate it; a spawn before its scene is READY logging once.
- **Picking and the pointer:** ray picking in a stage3d and a stage2d, sprites by their texels, the pointer's hover, press, and click over actors, and the pointer captured by a press on an interactive actor; app-touch, gfx-pick, and gfx-tilemap become same rows.
- **Layered stages:** a stage drawn over another with the depth cleared (a weapon over the world).
- **What 3D milestone 2 didn't need:** lit and custom-material sprites, and whatever the catalog holds then.
- **Orientation on phones** (Rob's; rotation today is only a resize the presentation refits): `wgf_window_request_orientation(LANDSCAPE | PORTRAIT | ANY)` locking where the platform allows (Android's Chrome, fullscreen only), read back with `wgf_window_get_orientation`, `wgf_window_is_orientation_locked`, and `wgf_window_can_lock_orientation` (CONVENTIONS.md's request/is/can); where a request can't lock, a built-in "rotate your device" overlay that pauses the game, on by default, a game may turn off to handle it itself; the orientation's change as an event and a probe, so an autopilot can simulate a rotation; safe-area insets (notches) fed into the presentation and the UI's anchoring; and optionally a design resolution per orientation. No prior art in libwgt or wgrender-c.
- **From the racer's friction** (FRICTION.md): a glTF file's nodes counting as blocks above a scene's block (no empty blocks for the nodes in between), and a `light` kind in scenes with its shadow keys; a model line's material numbers in scenes (`model roughness= metallic=`), so a prefab keeps its look without code; an environment's brightest direction (its sun), read from its image, so a game aims its light from the data; and a recording that keeps inputs made while its start's loads were in flight in order (a `wait` on what the game showed, where today they are all filed at frame 0).
- **Random generators of a game's own** (FRICTION.md: the racer's one generator): a generator as a handle, seeded, beside `wgf_random`, so a world's layout draws its own numbers and an autopilot's seed stays the game's.
- **Export lists from a bundler's tree-shaking** (Rob's): what a JS or TS program calls, for its trimmed host, read from the bundle (Rollup's `renderedExports` of `wgf.js`, a plugin of about 20 lines) in place of the identifier scanner (`jsbinding.names_in`). Tried on the JS Asteroids: the same 68 calls and 35 enums; where the scanner links what a dead function or a comment names (Jolt, 202 KB of gzip to 425), the bundle doesn't, and where a call is computed (`wgf["wgf_" + n]`) the bundle keeps every call (bigger, never broken) where the scanner misses it. The typed layer's frozen objects need one module a kind (`import * as Actor`) to shake as `wgf.js`'s named exports do; the Haxe path the same from a macro after its dead-code elimination, in place of reading its output's quoted keys. And a trimmed host fails naming a call it lacks, not "undefined is not a function".
- **Toolchain on demand** (Rob's): `wgf setup`, which the first C build or trimmed export that finds no Emscripten offers, fetches the Emscripten libwgf pins (CI's version) from emsdk's own per-release archives for this OS (the LLVM, Binaryen, and Emscripten bundle, Node, and on Windows Python) into a cache libwgf owns, with a marker named for the version so a new pin fetches again; it never touches PATH or a user's emsdk, and a user's own install is taken when it has the pinned version, checked by finding and running its emcc. JS, TS, and Haxe developers on prebuilt hosts (the item above) never need it. `wgf.cmd` finds Python 3.12 or newer on Windows (`py -3`, then `python`) and, with none, offers python.org's embeddable zip into the same cache and runs `wgf` with it: a small exception to "nothing in shell", its only job finding or fetching Python, stated in CONVENTIONS when it lands (the Linux and macOS `wgf` stays the Python script it is). The flow is that of Rob's Beef fork (`wasm/fetch_wasm.bat`, `IDE/src/BuildContext.bf`'s `GetEmccPath` and its install prompt: offered at the first wasm build, a versioned marker, its own cache, a user's install checked by its emcc), without hosting a repack as it does. It is built on what exists, not a new mechanism: `tools/usercache.py` and the pattern of `setup_mingw.py` and `setup_shdc.py` (pinned, fetched into the per-user cache at first need, never whatever is on PATH unless pointed at on purpose). And friendlier defaults for a developer who doesn't target the web, since Emscripten is only the web's compiler (the desktop is hxcpp and the native compiler): `wgf build` (web by default today) and `wgf export` (both by default) build what the machine can and say plainly what was skipped and how to get it ("skipping web: no Emscripten; `wgf setup --web` fetches the pinned one"), where today they stop; an explicit `--web` still fails, with that message. Once prebuilt hosts exist, `serve` and a full-host web build need no Emscripten at all; only a trimmed export does.
- **Starter templates:** `wgf new` offers a few (top-down, platformer, menu-driven).
- **Jam simulations:** several fresh, isolated sessions, across genres, each given only the docs, `wgf new`, a random jam theme, and a time limit, and each shipping to Pages. Their friction logs are the result, triaged as a milestone's are.

Done when: every catalog feature has an example in the browser check and the size table; `wgf new` offers the starter templates; a jam game goes from `wgf new` to deployed on Pages in one sitting, checked by doing it (the jam simulations); and every jam simulation's friction is triaged.

## Later, when its condition holds

Each starts when something anyone can check is true.

- **physics2d (Box2D v3)**: when a game or example on the ROADMAP needs 2D rigid bodies, joints, or contact resolution; no game in milestones 1 to 3 does, and Asteroids' overlaps are the ecs collider's.
- **Dear ImGui (cimgui), the developer UI**: when a milestone's game needs an in-game inspector (SPEC.md, "Not in v1").
- **WebGPU behind a build option**, then as the default: libwgt's condition (its ROADMAP, "Later"): Firefox ships WebGPU on Linux, Chrome on Linux covers the common GPUs, and every example passes on WebGPU in CI, with an automatic fall back to WebGL2 and a persisted switch.
- **Native hot reload** (hxcpp or C): when a game's desktop-only bug needs the reload loop to find; the browser is the everyday loop. Not through cppia as it measures now (HISTORY.md, "Native hot reload stays deferred").
- **A CPU particle mode, beside the GPU emitters**: when a game needs particles that react after they are born (steered, colliding, attracted), which a stateless GPU particle can't be; milestone 1's CPU 2D emitter, retired at milestone 2's step 11, had that mode, which libwgt's TASKS.md wanted.
- **Threads on the web**: when a benchmark shows a load or a system that a worker would take off the main thread by more than a frame's budget.
- **wgrender-c's stress scene** (`tools/bench/stress.c`, the scene every binding ported): when a binding's per-call cost at thousands of actors is the question; milestone 3's stress run is the likely one. Its page harness comes with milestone 2 (step 1).
- **Cascaded shadows**: when the racer's single fitted sun map can't keep the car's contact shadow sharp at the shadow distance its track needs (a texel larger than a tenth of the car's width on the benchmark lap), measured; libwgt's and wgrender-c's open "phase 3".
- **A minified build of a JS program, checked** (wgrender-c measured its JS binding under esbuild's property mangling): when a JS program is shipped minified. The binding keeps the rules that made it safe there (HISTORY.md, "The JS binding, the one way JS reaches the host").
- **A scene as JSON, outside the runtime**: a tool turning a `wgf-scene` file into JSON and back, the same scene both ways, for editors and scripts that want a tree of objects; when a tool or an editor a game uses needs one (the runtime reads only the line format).
- **AI players, an autopilot `set` command, and a supported way to record with no one there** (FRICTION.md: the racer's lap, recorded through Xvfb and xdotool; HISTORY.md, "Milestone 2, step 4, the racer's friction"): when a game needs AI opponents (or an attract mode), or recording a game's autopilots becomes a burden. Weighed then: an AI behavior feeding the game's actions, a `set` command writing a named value the game reads (a probe's opposite), and a headless run driven a frame at a time by a script.
- **glTF `extras` read** (FRICTION.md: the racer's centerline, written beside its track as Haxe): when a game's data must ride in a glTF file that a tool other than its own writes (an editor's custom properties, a level made in Blender), so it can't be written beside the file.
- **A fault policy that runs on past a throw** (wgrender-c's guest ABI had one): when a game should keep running after a callback throws; libwgf ends the run.
