What is left to build, in order. A finished item is deleted from this file, not ticked off, and its record moves to [HISTORY.md](HISTORY.md) in the same commit. What exists now is [ARCHITECTURE.md](ARCHITECTURE.md).

## Finishing libwgf: the comparison with helix

Rob's (2026-11-19): libwgf is finished so that a pure C and wasm engine can be compared with helix. Done means three things: **helix-raylib's feature set as a floor** (what a helix-raylib program can do, a libwgf program can, in libwgf's own way: feature parity, not its API, and not only what it does); **helix's benchmarks** (the bunnymark and the animated robots, `../helix/docs/benchmarks.md`) run on libwgf beside helix-raylib's rows, speed and size; and **Wardens** (helix's engine trial) built on libwgf and graded as helix's entrants are. The blocks below are in order; each item has its tests, an example where there is something to see, its calls in the bindings and the feature test, and a look at how helix-raylib and helix-legacy did it (read-only).

1. **The core systems** (below), in their order.
2. **The game structure block** (below), in its order.
3. **Parity, the small gaps** (from the parity checklist, the rows helix-raylib has and libwgf has nowhere planned):
   - shape tests as plain math: a point in a rectangle, circle, triangle, polygon; segments; boxes and spheres; a ray against a sphere, a box, a triangle;
   - splines: a point along a linear, Catmull-Rom, or Bézier path, and drawing one;
   - a texture made from bytes, and updated;
   - a lost GPU context recovered (phones and browsers drop WebGL when backgrounded);
   - text's letter and line spacing;
   - the last pad button pressed (a rebinding screen's, beside the last key);
   - a shuffled sequence with no repeats (with the seeded generators, Wardens' item 5).
4. **The UI on RmlUi, for menus.** RmlUi (MIT; documents in RML, styled in RCSS) as a part of the ui layer a program links only by loading a document, beside today's immediate UI on Clay, which stays for HUDs and small UIs: documents and their elements as typed handles, events read each frame (no callback crosses the API), its geometry, textures, and scissor drawn by gfx, its text through fontstash. It brings the parity checklist's controls (toggles and check boxes, a choice selector and a dropdown, a slider, text fields with the clipboard and a phone's keyboard, scrolling lists, tabs, tooltips), menus drawn from images (nine-slice decorators, every state), transitions and animations, and focus by keys and pads (`nav-*`, `tab-index`). Measured (2026-11-19, the same menu at -Oz): RmlUi 264 KB of gzip, Clay 33, Yoga 26 (layout alone; not taken). The racer's and Asteroids' screens stay on Clay.
5. **Wardens** (below), what it needs, then the game.
6. **Parity, the rest:** the parity checklist's remaining rows, each a capability helix-raylib has: rings, sectors, arcs, ellipses, and gradients in 2D; a texture fill (radial cooldowns); textured polygons and tiled draws; 3D debug draws (cylinder, capsule, triangle, wire sphere, a model as wireframe, a skeleton); color math (HSV, brightness); multiply and premultiplied blending; heightmap meshes, meshes updated in place, vertex colors; images on the CPU (load, read a texture's pixels, generate noise and gradients); a cubemap for a custom shader; frame stats (draw calls, triangles, GPU bytes); a free-fly and a first-person camera; particles' wander, orbit, pulse, shells, local space, and alignment to motion; tilt, and touch from the mouse; input recorded and replayed; bitmap fonts; raw audio streams and a callback; listing a directory; a log callback; a screenshot saved; a window's resize event and icon. Then milestone 2.5's items below that helix-raylib also has (picking, rounded rectangles, rumble, safe areas and orientation).
7. **The comparison.** The bunnymark and the robots on libwgf, on the web and natively, beside helix's rows on this machine; Wardens' grades beside helix's entrants'; the parity checklist's rows, each as libwgf has it, and what libwgf has that helix-raylib doesn't. Written up in HISTORY.md.

Out of the parity work, as not libwgf's (the checklist's skips): desktop window chrome, the program owning the frame loop, warping the mouse; path, string, and codepoint helpers, compression, Base64, and hashes (the host language's); VR stereo; rlgl's immediate vertices, matrix stack, and global GL state; image editing on the CPU, pixel formats, and exporting images, meshes, and code; raygui's color picker, grid, built-in icons, style files, and draggable windows; OBJ, IQM, VOX, and M3D models.

## Core systems

The systems nearly every game needs, in this order, each a 2D and a 3D half where it has them, carrying what helix-legacy (`../helix-legacy`) did.

1. **2D collision on actors.** The math is done (`wgf_collide2d.h`); left: rectangles, polygons, and segments as a collider's shape beside today's circle, its overlaps' push out in the trigger events; a broadphase so a scene of a few thousand finds its pairs (helix-legacy's `SpatialHash2D`); and a 2D body component that moves and slides each tick with gravity, grounded, against colliders and a tilemap's solid cells (helix-legacy's `Body2D`).

Done when every item's calls are in the bindings and the feature test, and each has an example in the browser check.

## Game structure

What a game of any genre writes in its first day, in this order, each done as a core system is, carrying helix-legacy's.

1. **Screens and scene flow.** A game as a stack of screens (title, play, pause, game over): push, pop, and replace, a screen's stages and actors its own, paused under the one on top and resumed; transitions between two (fade, slide, wipe, iris, each on an ease, the swap at the middle); a loading screen with one progress over every asset a screen asks for (`wgf_asset_group_*`); and pausing when the page or window loses focus. helix-legacy's `scene/Flow.hx`, `Loader.hx`, `LoadingScreen.hx`, and `scene/transition/`.
2. **2D animation.** Sprite sheets (a grid, or a packer's atlas of named frames), clips of frames at a rate (looping, once, ping-pong), an animator on a sprite actor playing clips by name, events on a frame, and directions (a clip a facing); a sheet made from a folder of frames by a tool. helix-legacy's `render2d/SpriteSheet2D.hx`, `SpriteAnimator2D.hx`, and `tools/gen_sprite_sheet.py`.
3. **Tilemaps.** Tiled's maps (`.tmj`, its tilesets `.tsj`): tile layers drawn as one actor each (the sprite batch's records, or a mesh, which the plan measures), object layers read as actors and prefabs by class with their properties, animated tiles, a cell read and set, and the solid cells 2D move-and-slide collides with. helix-legacy's `tiled/`; today's `examples/c/gfx-tilemap` rebuilt on it.

Done when every item's calls are in the bindings and the feature test, and each has an example in the browser check.

## Wardens: what it needs, then the game

Helix's engine trial Wardens (`../helix/docs/trials/templates/wardens/`: `spec.md`, the game naming no engine; `grading.md`, its 37 items; its assets, every one CC0), built on libwgf once what it needs is here, and graded as helix's entrants are (helix-raylib, raylib in C, three.js), so libwgf's score stands beside theirs. What it needs that the blocks before don't give, in order:

1. **Skeletal animation** (milestone 3's first item, moved here): glTF skins, and the animation player redesigned as SPEC says, on wgrender-c's measured joint texture (every joint matrix of the frame in one float texture: 100 animated characters 15.2 to 2.1 ms) and libwgt's player: clips by name, crossfades (Wardens' 0.2 s), layers with a bone mask (an attack from the waist up while the legs run on), shared skeletons (a character of separate part models on one skeleton, animated together, a part swapped while it plays without a jump), sockets (a model held at a bone, following it through every clip), and a custom material and a tint on a skinned model (Wardens' hit flash on an animated, lit enemy); helix's animated robots benchmark on it.
2. **A game's menus from images:** on RmlUi (block 4 above): nine-slice decorators in every state (normal, focused, pressed, disabled), a slider, a button with an image (Wardens' cards), every control reached by the keyboard, a pad, the pointer, and touch; and nine-slice textures for sprites and immediate drawing.
3. **Touch controls:** an on-screen stick that appears where a finger lands outside the UI and drives an action as a pad's left stick does, ended when the finger lifts; on-screen buttons bound to actions; neither moving anything under it.
4. **Run options:** the program's arguments by name (`--enemies=200` natively, `?enemies=200` in a page's address), read the same way on both (the bunnymark reads `location.search` by hand today).
5. **Random generators of a game's own** (milestone 2.5's, moved here, FRICTION.md: the racer's one generator): a generator as a handle, seeded, beside `wgf_random`, so a world's layout draws its own numbers and an autopilot's seed stays the game's (Wardens' `seed=N`).
6. **The game:** `games/wardens/`, with helix's spec and assets unchanged, in Haxe on libwgf's public API, a page and native; its native program shot by helix's `take_screenshots.py` and graded with helix's `review-brief.md`, the grades recorded in HISTORY.md beside helix's entrants'.

Done when Wardens is graded.

## Milestone 2.5: jam-ready

After the comparison, unless an item is helix-raylib's too (block 6 above).

libwgf is a framework, not one game's library: a game jam must not have to stop and add a feature under a deadline (SPEC.md, "Done means games", 2.5). After the racer, what was trimmed from wgrender-c and libwgt and no game has brought back is restored (the catalog below, less what milestone 2 carries), each feature with a showcase example in the browser check and the size table, wgrender-c's suite the model; breadth stays cheap, since a program links only what it calls. Outlined here; planned in full once milestone 2 closes.

In order of what a jam game hits first:

- **Picking and the pointer:** ray picking in a stage3d and a stage2d, sprites by their texels, the pointer's hover, press, and click over actors, and the pointer captured by a press on an interactive actor (point-and-click, tilemaps, menus in the world, and milestone 3's click-to-move); app-touch, gfx-pick, and gfx-tilemap become same rows.
- **Shaders warmed before the first frame** (wgrender-c's open task: a first frame of about 220 ms on WebGL2 while its pipelines compile), so a game's first impression isn't a stall.
- **2D drawing:** rounded rectangles and borders, a line thickness and a corner radius on shapes, text slices drawn and measured without copying, and clip actors (scrolling regions).
- **Layered stages:** a stage drawn over another with the depth cleared (a weapon over the world).
- **Textures:** a settable placeholder.
- **What 3D milestone 2 didn't need:** lit and custom-material sprites, and whatever the catalog holds then.
- **Gamepads' rest** (wgrender-c's "gamepads later"): rumble, connect and disconnect events, and a mapping database for pads the browser and SDL's table don't know.
- **From Asteroids' friction** (FRICTION.md): sounds without files (a sound from samples made in code, and a starter sound in the templates); timers on the tick clock owned by a behavior or the runtime, ended with their owner (`after`, `every`, a cooldown, an actor's blink); an area query (anything on these layers within a radius, no actor needed); named collider layers in the scene format; the UI's default focus when the last input was keys or a pad, and a guard so a press begun before a screen appears doesn't activate it; a spawn before its scene is READY logging once.
- **Orientation on phones** (Rob's; rotation today is only a resize the presentation refits): `wgf_window_request_orientation(LANDSCAPE | PORTRAIT | ANY)` locking where the platform allows (Android's Chrome, fullscreen only), read back with `wgf_window_get_orientation`, `wgf_window_is_orientation_locked`, and `wgf_window_can_lock_orientation` (CONVENTIONS.md's request/is/can); where a request can't lock, a built-in "rotate your device" overlay that pauses the game, on by default, a game may turn off to handle it itself; the orientation's change as an event and a probe, so an autopilot can simulate a rotation; safe-area insets (notches) fed into the presentation and the UI's anchoring; and optionally a design resolution per orientation. No prior art in libwgt or wgrender-c.
- **From the racer's friction** (FRICTION.md): a glTF file's nodes counting as blocks above a scene's block (no empty blocks for the nodes in between), and a `light` kind in scenes with its shadow keys; a model line's material numbers in scenes (`model roughness= metallic=`), so a prefab keeps its look without code; an environment's brightest direction (its sun), read from its image, so a game aims its light from the data; and a recording that keeps inputs made while its start's loads were in flight in order (a `wait` on what the game showed, where today they are all filed at frame 0), its start's asset tasks counted with core's loads (an ensured start isn't, so its recording counts from the program's first frame); a scene's lister, so a scene ensured ahead brings the files its lines name (its models' files, and theirs), as a glTF file's buffers and images come with it. From part 7: a frame's draws and instances, read by a program and published as a probe (libwgt's `get_last_frame_stats`); soft particles, fading where they near what is behind them (the frame's depth read by the particle shader, after step 12's targets); a wheel's sliding speed beside its slip ratio, which pegs at 10; and text over the camera-facing sprite it labels kept in front at a distance (a depth offset toward the camera). From part 8: effects applied before the HUD (a call that applies them mid-frame, or an effect over the stages alone), so a game's HUD and the UI draw over an effect untouched, where today an effect's shader leaves their rectangles alone by hand; an effect given the frame's depth and the previous frame (a motion blur, a depth of field); a read-back that answers a frame or two later without stalling the next frame's update (a fence, polled), so a game can read mid-race; a texture drawn mirrored (a negative source width to `wgf_draw_texture_region`, or a sprite's flip; and `wgf_sprite.h` saying a negative scale mirrors a sprite, which it does); `wgf build` and `wgf serve` packing a game's `shaders/*.glsl` as they compile its Haxe (or a `wgf pack-shader`), so a game's own tool needn't find libwgf; a frame's GPU time measured beside its main-thread time, so a second view's cost on a weaker GPU shows; and `wgf dump` writing an emitter's `size=` and `color=` beside its keys, which read as two settings more.
- **From the combination scenes** (milestone 2, step 13, HISTORY.md): a UI drawn into a render target reads the pointer in the screen's pixels while it is laid out in the target's (scene-showroom's click on a button where it shows misses it at a render scale below 1). Rob's direction, both decided at 2.5's planning: the main fix is a **render scale in libwgf's presentation** -- the frame drawn at a fraction of the window's pixels and scaled up, so libwgf knows the mapping and the UI's pointer needs no call (phones will want it for performance too); and, for a UI really shown in a texture (an in-game monitor, a picture-in-picture panel), a **pointer area** (`wgf_ui_set_pointer_area(x, y, w, h)`, the screen pixels where the UI's target is shown). A UI on a 3D surface waits for 2.5's picking (a ray to the surface's UV). And a panel placed anywhere but the screen's middle without a box the screen's size around it (the root's alignment and padding settable after `wgf_ui_begin`).
- **Starter templates:** `wgf new` offers a few (top-down, platformer, menu-driven).
- **Jam simulations:** several fresh, isolated sessions, across genres, each given only the docs, `wgf new`, a random jam theme, and a time limit, and each shipping to Pages. Their friction logs are the result, triaged as a milestone's are.

Done when: every catalog feature has an example in the browser check and the size table; `wgf new` offers the starter templates; a jam game goes from `wgf new` to deployed on Pages in one sitting, checked by doing it (the jam simulations); and every jam simulation's friction is triaged.

## Milestone 3: an ARPG vertical slice with co-op

One village at night, the first scene of Rob's "Whispers in the Shadows" (SPEC.md: a town whose townsfolk put on red hooded cloaks and try to sacrifice you), one player class with three abilities (the modular character dressed as a noir investigator through wearables), three enemy types with navmesh pathing (among them Rob's cultist, re-rigged to Quaternius's CC0 Universal Animation Library, its Mixamo files kept out of every public repository; a townsperson turning cultist a replicated wearable swap), one co-op puzzle (a rune-locked crypt door opened together, its runes shared world state the server resolves), loot drops, an inventory, and 2 to 4 players in co-op through a central server. It proves skinned animation with blending, many lit instances, navmesh and AI, an authoritative server, and replication. The village is 1920s New England, from a small owned kit of about a dozen low-poly modular pieces modelled in Blender with Rob directing (his Asset Store village can't be redistributed, and no CC0 kit of the period is known), its people one base body with a period wardrobe; to confirm with Rob at planning (SPEC.md, "Art"). Planned in full once milestone 2 closes.

From the references, for a crowd of lit, animated characters in a town at night (each planned with milestone 3, ranked by what the scene needs; skinning and the animation player came first, and moved to Wardens' block):

1. **Instancing's next phase** (wgrender-c's PLAN-instancing phase 5, built by neither): a light set per instance, so characters under different torches still share a draw; see-through runs; and libwgf's own, from shadowbench: a material's factors in the instance record (its color, metal, roughness, emissive), so parts that differ only in those numbers, a tinted crowd's, share a draw too, since every separate draw costs the browser's GPU process (HISTORY.md, "shadowbench's cliff"). And from scene-depot (step 13), the CPU a model costs when nothing about it changed: one walk of the stage's tree a draw where there are six, a model's normal matrix and linear tint kept until its transform or tint changes, and a 3D label's layout kept until its text changes.
2. **Sprites that cast shadows** (alpha-tested quads in the depth pass) and **lit particles** (spells and torches lit by the scene: wgrender-c's "mostly wiring", the lights picked from an emitter's bounds): both open in wgrender-c and libwgt.
3. **Point-light shadows**, for the lanterns and torches a village at night is lit by: six maps a light, one each way (a cube, or six layers of the depth array), where today a point light's casting is refused (`wgf_light.h`); open in libwgt's TASKS, and left open by milestone 2 since the racer's sun needed none (HISTORY.md, "Milestone 2's plan"). How many may cast at once is the plan's to measure, as shadowbench measured the directional and spot maps.

## Distribution: when the API settles

Rob's: deployment work is premature while the API is still moving, since a published host or a pinned `wgf setup` promises developers a stable API. Condition: milestone 3 is closed, and a public API change no longer lands every few commits.

- **Prebuilt hosts.** One full host per libwgf version (not tiers of 2D, 3D, and physics), built in CI and published outside git (GitHub Releases; npm, with `wgf.js` and its `.d.ts`; haxelib), never committed. `build`, `serve`, and `run` copy it in and never link, so they need no Emscripten; `export` always trims (a release is trimmed by definition: no `--trim` flag), locally with Emscripten or in the game template's Pages workflow, and with neither it ships the full host and says so ("untrimmed, ~600 KB; `wgf setup --web` or the Pages workflow trims it"). Measured (2026-10-10): the full release host is 522 KB of gzip of wasm (608 with its JS and the whole binding); trimmed, the racer's is 501 and Asteroids' 153. Tiers only if the jam simulations show people who neither install Emscripten nor use CI, whom 600 KB hurts. Post-link trimming with wasm-opt doesn't work (the function table's 1,005 entries keep everything reachable: Asteroids' 493 KB against the linker's 153), so trimming stays the linker's.
- **Export lists from a bundler's tree-shaking** (Rob's): what a JS or TS program calls, for its trimmed host, read from the bundle (Rollup's `renderedExports` of `wgf.js`, a plugin of about 20 lines) in place of the identifier scanner (`jsbinding.names_in`). Tried on the JS Asteroids: the same 68 calls and 35 enums; where the scanner links what a dead function or a comment names (Jolt, 202 KB of gzip to 425), the bundle doesn't, and where a call is computed (`wgf["wgf_" + n]`) the bundle keeps every call (bigger, never broken) where the scanner misses it. The typed layer's frozen objects need one module a kind (`import * as Actor`) to shake as `wgf.js`'s named exports do; the Haxe path the same from a macro after its dead-code elimination, in place of reading its output's quoted keys. And a trimmed host fails naming a call it lacks, not "undefined is not a function".
- **Toolchain on demand** (Rob's): `wgf setup`, which the first C build or trimmed export that finds no Emscripten offers, fetches the Emscripten libwgf pins (CI's version) from emsdk's own per-release archives for this OS (the LLVM, Binaryen, and Emscripten bundle, Node, and on Windows Python) into a cache libwgf owns, with a marker named for the version so a new pin fetches again; it never touches PATH or a user's emsdk, and a user's own install is taken when it has the pinned version, checked by finding and running its emcc. JS, TS, and Haxe developers on prebuilt hosts (the item above) never need it. `wgf.cmd` (a plain launcher, finding `py -3` or `python`, lands before this) gains, with no Python 3.12 or newer found, an offer of python.org's embeddable zip into the same cache and runs `wgf` with it: a small exception to "nothing in shell", its only job finding or fetching Python, stated in CONVENTIONS when it lands (the Linux and macOS `wgf` stays the Python script it is). The flow is that of Rob's Beef fork (`wasm/fetch_wasm.bat`, `IDE/src/BuildContext.bf`'s `GetEmccPath` and its install prompt: offered at the first wasm build, a versioned marker, its own cache, a user's install checked by its emcc), without hosting a repack as it does. It is built on what exists, not a new mechanism: `tools/usercache.py` and the pattern of `setup_mingw.py` and `setup_shdc.py` (pinned, fetched into the per-user cache at first need, never whatever is on PATH unless pointed at on purpose). And friendlier defaults for a developer who doesn't target the web, since Emscripten is only the web's compiler (the desktop is hxcpp and the native compiler): `wgf build` (web by default today) and `wgf export` (both by default) build what the machine can and say plainly what was skipped and how to get it ("skipping web: no Emscripten; `wgf setup --web` fetches the pinned one"), where today they stop; an explicit `--web` still fails, with that message. Once prebuilt hosts exist, `serve` and a full-host web build need no Emscripten at all; only a trimmed export does.
- **A dev container** (Rob's), as a supported option, never a requirement: `.devcontainer/devcontainer.json` on the official `emscripten/emsdk:<the pinned version>` image with Haxe, hxcpp, and Python, `wgf serve`'s port forwarded, so the web loop runs with nothing installed (GitHub Codespaces too: open the repository, `wgf serve`, play in a browser tab), built and smoke-tested in CI so it stays working. It doesn't replace `wgf setup`: desktop builds stay native (a container makes no MSVC or macOS binary, nor easily runs a window); it is an environment where setup has nothing to fetch.

## Later, when its condition holds

Each starts when something anyone can check is true.

- **physics2d (Box2D v3)**: when a game or example on the ROADMAP needs 2D rigid bodies, joints, or contact resolution; no game in milestones 1 to 3 does, and Asteroids' overlaps are the ecs collider's.
- **Dear ImGui (cimgui), the developer UI**: when a milestone's game needs an in-game inspector (SPEC.md, "Not in v1").
- **WebGPU behind a build option**, then as the default: libwgt's condition (its ROADMAP, "Later"): Firefox ships WebGPU on Linux, Chrome on Linux covers the common GPUs, and every example passes on WebGPU in CI, with an automatic fall back to WebGL2 and a persisted switch.
- **Native hot reload** (hxcpp or C): when a game's desktop-only bug needs the reload loop to find; the browser is the everyday loop. Not through cppia as it measures now (HISTORY.md, "Native hot reload stays deferred").
- **A CPU particle mode, beside the GPU emitters**: when a game needs particles that react after they are born (steered, colliding, attracted), which a stateless GPU particle can't be; milestone 1's CPU 2D emitter, retired at milestone 2's step 11, had that mode, which libwgt's TASKS.md wanted.
- **Threads on the web**: when a benchmark shows a load or a system that a worker would take off the main thread by more than a frame's budget.
- **wgrender-c's stress scene** (`tools/bench/stress.c`, the scene every binding ported): when a binding's per-call cost at thousands of actors is the question; milestone 3's stress run is the likely one. Its page harness comes with milestone 2 (step 1).
- **Cascaded shadows**: when the racer's single fitted sun map can't keep the car's contact shadow sharp at the shadow distance its track needs (a texel larger than a tenth of the car's width on the benchmark lap), measured; libwgt's and wgrender-c's open "phase 3".
- **A minified build of a JS program, checked** (wgrender-c measured its JS binding under esbuild's property mangling): when a JS program is shipped minified. The binding keeps the rules that made it safe there (HISTORY.md, "The JS binding, the one way JS reaches the host").
- **A scene as JSON, outside the runtime**: a tool turning a `wgf-scene` file into JSON and back, the same scene both ways, for editors and scripts that want a tree of objects; when a tool or an editor a game uses needs one (the runtime reads only the line format).
- **AI players, an autopilot `set` command, and a supported way to record with no one there** (FRICTION.md: the racer's lap, recorded through Xvfb and xdotool; HISTORY.md, "Milestone 2, step 4, the racer's friction"): when a game needs AI opponents (or an attract mode), or recording a game's autopilots becomes a burden. Weighed then: an AI behavior feeding the game's actions, a `set` command writing a named value the game reads (a probe's opposite), and a headless run driven a frame at a time by a script.
- **glTF `extras` read** (FRICTION.md: the racer's centerline, written beside its track as Haxe): when a game's data must ride in a glTF file that a tool other than its own writes (an editor's custom properties, a level made in Blender), so it can't be written beside the file.
- **macOS presets** (wgrender-c had `macos-arm64`, written and not run there): when someone can build and run them on a Mac in CI or by hand.
- **The references' benchmarks** (from milestone 2's step 15, Rob's: features first): wgrender-c's loading example matched as an asset-loading row, its loadbench and startup timing (`measure_example_startup.py`, from the `performance.mark`s libwgf leaves: cold, warm, and hot starts) as rows, a session on Rob's phone (frame times and startups beside the reference machine's; spritebench's 2D cases on the batch there, which decides whether 2D sprites move onto it), and every side-by-side row that differs saying why: when a game's load, startup, or phone frame time is a FRICTION.md entry, or at Distribution, whichever is first.
- **Lightmaps** (wgrender-c's open task): when a static scene's lighting costs more of the frame budget than baking it would save, measured.
- **Blended sprites in 3D as small records** (spritebench: 16,000 blended sprites 31.1 ms against 10.2 masked, the difference each one a whole stage item walked, sorted, and moved): when a game's see-through sprites in 3D number in the thousands; libwgt's `transparent_t`, the see-through things sorted as a depth and an index, not as items.
- **A persistent instance buffer** for placements that don't move (wgrender-c's PLAN-instancing phase 5): when uploading a frame's instance records shows in a benchmark's frame times.
- **A large download's arrival without a stall** (wgrender-c's open task: 64 MB copied into the wasm heap stalls a frame about 80 ms): when a game streams a file that size.
- **Float (HDR) render targets, and an HDR framebuffer with bloom**: when a game's look needs them (step 12 carries 8-bit targets).
- **A fault policy that runs on past a throw** (wgrender-c's guest ABI had one): when a game should keep running after a callback throws; libwgf ends the run.
