# libwgf history

The record of what was built and decided, and why. When a step leaves the [ROADMAP](ROADMAP.md), done or dropped, its record moves here in the same commit: the design as it was, the decisions, what was built and measured, and what was tried and dropped. Entries keep the text they were written with and aren't rewritten when later work supersedes them, so a name or path here may since have changed. For how libwgf works now, read [ARCHITECTURE.md](ARCHITECTURE.md) and the headers.

libwgf is a clean start in the line of wg-core, librl, wgrender, and libwgt (libwgt's `docs/LINEAGE.md` summarizes the line). Those libraries are its references: their code is carried over where it works, and redesigned where it doesn't, each such decision recorded here with its reason.

## Milestone 1's plan (2026-10-05)

Decided before building, from reading libwgt (its docs, core, platform, app, and tools), wgrender-c (its Haxe and JS bindings, the guest host, Clay, particles, and audio), hotreload-hx, librl (its stash and version stamps), and flecs_wrapper-c.

**Carry libwgt's foundation, layer by layer, renamed.** libwgt is the latest of the line and the most carefully measured. Its handles, layers, optional parts behind hooks, the API checked by clang, the runtime and its tick clock, the platform layer, input, and the tools are carried into libwgf as each step needs them, renamed from `wgt_` to `wgf_`, and trimmed to what a milestone uses: milestone 1 carries the 2D half of gfx and none of the 3D (scenes, meshes, materials, lights, shadows, environments, custom shaders, picking), which milestone 2 brings. Why carry rather than rewrite: that code is tested and measured, and a rewrite would relearn what libwgt's HISTORY already records. Why trim: SPEC asks for a feature test reaching the whole public API, so every public call is one the feature test must exercise; an API carried before a game needs it is untested weight.

**What libwgt's conventions say that libwgf doesn't.** libwgt's rule "port wgrender's, don't redesign" is not carried: libwgf carries what works and redesigns what doesn't, recording why (this file). Everything else in libwgt's CONVENTIONS.md is libwgf's unless an entry here says otherwise.

**Layers.** math, core, platform, asset, gfx, audio, then the optional modules (ecs, ui; physics2d, physics3d, and net later), then app. SPEC lists asset after gfx and audio; libwgf keeps libwgt's order, asset under gfx and audio, since a resource made from a path is an asset (libwgt, Rob's decision of 2026-10-03): gfx and audio ask asset for a file, and asset never asks them for anything.

**ecs is a module of libwgf, where libwgt put it outside.** libwgt dropped its ecs layer (its HISTORY, "Dropped from the ROADMAP", 2026-10-02) so that a game not wanting flecs wouldn't carry it. SPEC makes flecs libwgf's ECS; the optional-parts rule answers libwgt's worry: ecs installs itself at a program's first entity, so a program that makes none links none of flecs. flecs comes from flecs_wrapper-c's vendored amalgamation (v4.0.5); the wrapper's own API isn't carried (a global world, fixed tables, ids without generations, registration that fails on a second run), since libwgf's handles and built-in components replace it.

**The entity and node split.** An entity is simulation: its transform (position, rotation, scale, in its parent node's space) and its components live in the ECS and change only at the tick rate. A node is presentation: each entity has one, which the ecs sets every frame to the entity's transform interpolated between the last two ticks, and its visual components (a shape, a sprite, text, an emitter) are nodes under it. So nodes stay the transform hierarchy that is drawn, entities attach to nodes, and a game reading an entity's position gets the simulated value, never an interpolated one. A move that shouldn't be interpolated (a wrap across the screen, a spawn) snaps: the entity's previous transform is set to its current one.

**Behaviors without callbacks.** A behavior is a Haxe class attached to an entity by name (a component holding the name and its parameters from the scene file). C keeps the lifecycle as events -- created, destroyed, trigger enter, trigger exit -- which the binding polls at the start of each tick and dispatches to Haxe objects; tick and frame are the binding's own loops over its live behaviors. Nothing crosses the binding as a callback but `wgf_app_run`'s, which SPEC's invariant allows.

**Colliders without a physics engine.** Asteroids needs overlaps (a bullet in a rock), not dynamics. The ecs's collider component (a circle or a box, layers and a mask) and its trigger events do that; Box2D waits on ROADMAP's condition (a game needing rigid bodies), which no milestone game meets.

**The Haxe binding: generated whole, calling the host directly.** wgrender's binding had two marshalling layers on the web (a JS binding, and Haxe over it) and a hand-written typed layer. libwgf generates both of Haxe's layers from the headers -- the raw externs and the typed API (an abstract per handle kind, `@:using` statics, inline throughout) -- and the JS target calls the host's exports itself, by quoted keys, with wgrender's runtime rules (no held heap views, one fixed malloc'd slot for returned structs, strings on the stack released per call). wgrender measured its two layers at about 3% more download than one; with one there is one marshaller to test. Hand-written Haxe is only sugar and the runtime (the guest ops, behaviors, hot reload).

**Handles typed per kind.** Every public handle parameter and return is a typedef of `wgf_handle_t` named for its kind (`wgf_texture_t`, `wgf_node_t`, `wgf_entity_t`), so the generator maps each to its Haxe type from the header alone, with no table to keep in step, and check_api can hold each section's calls to its kind. They are the same 32-bit value in C.

**Math values are returned, never taken.** libwgt passed vectors by value both ways. On wasm32 a struct parameter is passed by a pointer to a copy, which a JS caller would have to build in memory; so libwgf's setters take components (floats) and only getters return a math value (through the fixed slot). check_api holds the rule.

**One runtime call on every target.** wgrender's web host had a guest ABI of its own (`wgr_guest_register`). libwgf's guest calls `wgf_app_run` itself on every target: natively through hxcpp's `cpp.Callable`, on the web with the JS functions put in the wasm's table once (`addFunction`), each a dispatcher through a static the hot reload re-points. The host is libwgf built for the web with no `main`, exporting every public function (the full host, prebuilt, for development and hot reload); a game's export links a trimmed host, exporting only the calls its compiled guest makes (wgrender's full and trimmed, Rob's names), and measures it against the game's size budget.

**Natively, the binding links a staged archive.** wgrender compiled its C sources through hxcpp, because MinGW archives fail to link with MSVC's linker; libwgf follows libwgt's plan instead and links `out/<variant>/lib`'s archive, built by the same toolchain hxcpp uses (the MSVC presets for an MSVC hxcpp build), so the library is compiled once, with its own flags and checks, and never by a game's build.

**2D drawn through sokol_gl, particles on the CPU.** libwgt draws canvas sprites through its instanced sprite batch and particles through GPU emitters, both with shaders of its own (sokol-shdc, committed headers per backend). Milestone 1 draws shapes, sprites, text, and particles through immediate mode (sokol_gl, and sokol_fontstash for text), so it carries no shaders and no shader tooling; its particles are simulated on the CPU, which also lets them react after birth (libwgt's TASKS.md wanted that mode). The instanced batch and GPU emitters come with milestone 2's 3D, or sooner if a benchmark of a 2D example shows sokol_gl's recording as the frame's cost.

**asset, milestone 1's part.** libwgt's asset layer also caches in IndexedDB, revalidates, follows manifests and redirects, and streams. Milestone 1 needs files fetched on the web, read natively, and a fetch hook natively, so that is what it carries; the cache and the manifests come when a game's assets are large enough that the browser's own HTTP cache isn't enough (milestone 2's track and car, likely), and streaming with milestone 2.

**Audio formats.** WAV and MP3 (dr_wav, dr_mp3) natively, the same formats the web decodes, so the API means the same on every platform. Ogg Vorbis (libvorbis, which libwgt vendors after dropping stb_vorbis for its fuzz failures) comes when a game ships music.

**Scripted runs, deterministic.** SPEC's playthroughs need inputs over time and assertions, on the desktop headless and in a browser alike. The runtime reads a script (a file natively, a URL parameter on the web): inputs at frames, and assertions on probes -- named numbers a game publishes (`score`), and those the ecs publishes (entities by behavior). While a script runs, every frame lasts exactly one display frame of virtual time, so ticks and the seeded random generator make the same run on every machine.

**Hot reload: hotreload-hx's class swap.** librl's reload tore the guest down and rebuilt it from a stash the script kept by hand; hotreload-hx swaps the new bundle's classes in place (statics copied, objects given the new prototypes, new fields initialized), keeping every Haxe object and needing no stash. libwgf carries hotreload-hx's JS swap into its binding's runtime, and its rules: the swap between frames, never inside a call from C; only stable trampolines in C; a full host, never relinked by a reload. C's own state (entities, nodes, resources) never leaves the wasm, and the Haxe objects holding its handles keep them.

**"scene" means the data scene.** SPEC's scenes are files of entities, components, and prefabs (`wgf_scene_*`, the ecs module's). libwgt's `wgt_scene` was gfx's 3D root; when milestone 2 carries it, it takes another name.

## The repository, math, and core carried (2026-10-05)

libwgt's build (its presets, `wgf_layer()`, the MinGW toolchain file, the Emscripten pin at 5.0.7), its tools (headers.py and check_api.py, check_tools, variants, stage_variant, verify_builds, the browser driver and server, run_in_browser, run_in_xvfb, the Wine and remote Windows runners, setup_mingw, setup_system_packages), its math, and its core, renamed. Decisions on the way:

- **No threads or WebGPU presets.** libwgt's `-threads` and `-webgpu` web presets aren't carried: SPEC makes threads optional and every game runs without cross-origin isolation, and WebGPU waits on its condition (ROADMAP, "Later"). The Windows presets gain `-release`, for a game's desktop export.
- **math is headers alone.** Its operations are `static inline`, without libwgt's exported copies (HISTORY's plan: bindings do their own math, and no public call takes a math value), so the math layer is an interface target and `wgf_layer()` takes a layer with no sources.
- **core compiles sokol_time.** libwgt compiled every sokol implementation in platform, which core's clock then needed: core's tests linked the platform layer above it. libwgf's core compiles sokol_time itself (`wgf_core_sokol_impl.c`), so core links alone.
- **The identity is a section.** libwgt's `wgt_set_app_company` and `wgt_set_app_name` named no section; they are `wgf_identity_set_company` and `wgf_identity_set_product`, in `wgf_identity.h`.
- **check_api holds the two new rules**: a handle is its kind's type (`ANY_HANDLE` lists the calls that take any kind, with why), and a math value is never a parameter; its self-test has a break of each. fs's tasks are `wgf_fs_task_t`.
- **Wine's launcher failing.** libwgt's TASKS.md recorded `wgt_core_resource_test` failing once under Wine with "Application could not be started", right after the wineserver restarted, the program never having run; it happened here on the first verify (`wgf_core_fs_test`). As TASKS proposed, `tools/run_wine.py` now tells that message ("ShellExecuteEx failed", with a failing exit) from a program's own failure, and starts the program again, at most twice, saying so.
- **The handle kinds** are milestone 1's (core's, gfx's node, texture, and font, audio's sound and voice, asset's task) and ecs's new block (entity, scene, from 32); the 3D kinds come back with milestone 2, at their libwgt numbers.

## Bulk calls through caller-owned arrays (2026-10-05)

SPEC gained an invariant (Rob, 1776153): a call that reads or writes many objects takes a caller-owned array and a count, filled or read in one call; no shared scratch area (librl's was dropped: results overwrote each other between calls, and views broke when wasm memory grew), and no command stream within a process (wg-vf's, which wins only across a process or network boundary); heavy per-entity loops run as C systems, and scripts set intent. The hard rule gained the array form (CONVENTIONS, "Public API"): a `const float *`, `const int *`, or handle type's `const wgf_<kind>_t *` read, or the same without `const` filled, each followed by its `int count` (`<name>_count` for a call's second); kept by no call past its return; a filling call returning how many it filled. check_api holds it, its self-test with an array without a count, one alone, one returned, and one of doubles. The binding copies a Haxe array into wasm memory for the call's length and back, holding no view across calls (step 8); the ecs's per-entity work is C systems (step 6), as planned.

## Milestone 1, steps 1 and 2: closed (2026-10-05)

**Step 1, the repository** (af25cc6, and the array rule's commit): the docs, the build in layers, the presets, the vendored dependencies, the tools, and CI on GitHub Actions (`.github/workflows/ci.yml`: the Linux presets, the web presets with the runner's Chrome, and the MSVC presets on `windows-2025`, each through `tools/verify_builds.py --only`). The first CI run failed on Windows alone: the runner has a clang on PATH and no Emscripten, so check_api parsed for a Windows target, where `WGF_API` marks nothing, and found nothing exported; the parse now defines `WGF_API_PARSE`, under which the mark is the attribute everywhere (`include/wgf_api.h`), which clang keeps on a Windows target too.

**Step 2, math and core**, with what milestone 1 adds to libwgt's core:

- **`user:` paths**, the program's own files that last (a save, settings), apart from the files it ships with, whose root is the program's own directory natively: a high score written beside an installed game's executable would land where a user can't write. Natively they are under the user's data directory (`$XDG_DATA_HOME` or `~/.local/share`, `%APPDATA%`, `~/Library/Application Support`) by the identity, found the first time one is asked for, so an identity set first is used; on the web under the root's `.user/`, which the browser keeps as it keeps the rest. A request is refused, with a warning, where there is no such directory. Tested natively, under node, and across visits in a browser.
- **Probes** (`wgf_probe.h`), named numbers a program publishes, for scripted runs' assertions (step 3), the `wgf` tool's dump, and tests: 256 at most, names of 63 bytes from a small alphabet, listed in the order first set, emptied with core.
- **Random numbers** (`wgf_random.h`): PCG32 with one fixed stream, so a seed alone names the sequence, seeded from the clock as core starts, and by a script when one runs. Integers are drawn without the modulo's bias (Lemire's rejection). Its test checks seed 42's first four draws against values from a PCG32 written apart from the C, so every preset's run proves a seed's sequence is the same there; MSVC's C4146 (unary minus of an unsigned) in the rotate was written `(32 - rot) & 31`.

## Milestone 1, step 3, platform and app: closed (2026-10-05)

libwgt's platform (the window, keyboard, mouse, gamepads, touch, the headless window) and app (the runtime and its tick clock) carried, with gfx's frame, color, and the first of immediate mode, which a window needs to show anything. Decisions:

- **gfx's frame trimmed to one pass.** libwgt's frame records commands between sokol_gl layers -- scene draws, sprite batches, particles, depth clears -- and passes for render targets, with screen effects after. Milestone 1 draws only through immediate mode, so libwgf's frame is one sokol_gl recording drawn in one pass, keeping libwgt's grown context and its clip stack; the commands, targets, and effects come back with milestone 2's 3D, from libwgt's `wgt_gfx_render.c`.
- **Thick lines.** libwgt's immediate mode drew lines through GL's lines, a pixel wide whatever was asked; vector art, Asteroids', needs a line of a given width. libwgf's outlines, lines, and polylines take a thickness in logical pixels and are triangles: a polyline's corners mitred, and bevelled where a sharp corner's miter would reach past four half thicknesses. A polygon, convex or not, is filled by ear clipping (a fan, for one whose edges cross): a rock is concave. Points come in a caller-owned array, a first bulk call. Seen right natively, under Wine, and in a browser (the app-hello screenshots).
- **Dropped for now: the pointer over canvases, and the fps readout.** libwgt's app updated gfx's pointer (hover and press over interactive nodes) every frame; libwgf's UI hit-tests its own widgets (Clay), and Asteroids picks nothing, so the pointer is left until a milestone picks nodes. `wgt_loop_draw_fps` drew text, which comes in step 4; a game draws its own readout.
- **Scripted runs** (`app/src/wgf_app_script.c`, its format in `wgf_app_script_priv.h`): a text script, a line each, of inputs at frames (keys, typed text, the mouse, pads) and expectations on probes, with a seed and an end; parsed whole first, every line bounded and checked, a bad line logged with its number and the program ended; played a frame at a time, inputs delivered as the window's events before the frame's ticks, expectations checked after it. Natively from the file `LIBWGF_SCRIPT` names, on the web from `Module["wgfScript"]`, the text the page hands the module, read by quoted key. While one runs, every frame is a sixtieth of a second, so ticks and seeded random numbers make the same run on every machine, and a headless run doesn't wait for a display (`wgf_platform_priv_set_paced`). The result is logged, PASS or FAIL, failures as errors, since a page has no exit code: the tools judge the log, as they already did. Scripted pads replace the real ones from the first pad command. Tested headless through `wgf_app_run`: every kind of input reaching the program's ticks, the frames' time, the seed, a passing and a failing script, and 18 scripts the parser refuses. UBSan found `qsort` given the NULL array of a script with no commands.
- **The parts' tick.** core's part record gained `tick`, run after each of the program's ticks, for a module's systems at the tick rate (the ecs's, step 6).
- **A window on every platform.** app-hello, libwgt's hello without text, opens and draws on Linux (Xvfb), the web (headless Brave), and Windows: the MinGW build in a window under Wine on Xvfb (`tools/check_desktop.py --variant windows-x64-mingw-debug`, new: Wine runs on the same display), and both Windows toolchains' builds headless on sightblinder (`tools/run_remote_windows.py --then`, new: a tool run in the copied tree after the presets). A window on Windows' own desktop isn't checked by a tool: ssh's session has none, and CI's Windows runner has no GL 4.1. `tools/examples.py` builds the MSVC variants' examples with Visual Studio's generator, a configuration per build.

## Milestone 1, step 4, gfx in 2D, with asset: closed (2026-10-05)

asset came into this step from the next: textures and fonts are made from paths, and a path is an asset, so gfx's resources needed it first.

- **asset carried whole.** libwgt's asset layer (the web's fetch and cache, revalidation, offline, manifests, redirects, ensures, groups, pings, the native download hook) is 30 calls, fully tested, and checked across browser visits by `tools/check_asset_cache.py`; writing a thinner one would have meant proving it again. Its handles are typed `wgf_asset_task_t` (ensures, groups, pings, and the program's downloads are all asset tasks). libwgt's streamed sounds aren't carried (step 5 decodes whole), so its header no longer describes them; core's arrival hooks for them stay, unused, until a game streams music.
- **Textures** are libwgt's without compressed (KTX) files, render targets, a glTF file's images, the alpha copy picking reads, or a settable placeholder. One behavior changed: libwgt drew the checker while a texture was PENDING as well as once it FAILED; libwgf draws nothing while it loads and the checker only once it has failed, so the checker means a failure (SPEC: "A failed load logs once and draws a placeholder") and a game's own loading screen isn't covered in magenta. stb_image is built without HDR (for 3D environments).
- **Fonts and text** are libwgt's, without 3D text.
- **Nodes** are libwgt's tree, its cached transforms and its holes, without 3D, picking, posing, clip nodes, `look_at` (it took vectors), or the pickable flag. libwgt's canvas named its sprites, text, and shapes, and reached particles through a hook; libwgf's node kind record gained a draw, set by each type's first create, so a canvas names no type at all and a program links only the types it makes.
- **Shapes** were rewritten: libwgt's shape2d drew rectangles (rounded), circles, and lines; libwgf's draws rectangles, circles, lines, and polygons -- an Asteroids rock -- each as its outline's points placed through the node and drawn by immediate mode's fill or thick polyline, so a turned or scaled shape is drawn exactly as a plain one. Rounded corners wait for the UI (step 7), which draws its own.
- **Sprites** are a placed textured quad through sokol_gl (HISTORY's plan), with libwgt's centered default pivot; no nine-slice, alpha modes, materials, or facing.
- **Particles** are new: libwgt's emitters were GPU-simulated with shaders of their own; libwgf's 2D emitter simulates on the CPU, drawn through sokol_gl, with a rate spread along the emitter's path in the frame (a trail, not a clump), bursts, a capacity, life, direction, speed, a birth radius, gravity, drag, size and color over life, and squares or streaks; their randomness comes from `wgf_random`, so a scripted run's particles are the same every time (its test replays a seed vertex for vertex).
- **Tests**: libwgt's node, text, and draw tests carried and adapted; new texture, shape, sprite, and emitter tests; libwgt's browser pixel tests carried (the frame, textures, text, canvases), their render target, clip node, sprite batch, and GPU particle parts replaced by checks of what libwgf draws (a turned sprite, a turned polygon, a concave fill, a thick line, a pushed clip, a CPU particle under a camera).
- **Examples**: gfx-canvas, a 2D world under a zooming camera and a HUD canvas over it, with every node type. `tools/examples.py` had given every build the MSVC generator's per-configuration output directory, which also moved a web program out of its folder of the site; only the MSVC builds get it now. `examples/assets/textures/tiles.png` comes from libwgt, Whirling Gizmo's own (`examples/assets/CREDITS.md`).

## Milestone 1, step 5, audio: closed (2026-10-05)

libwgt's audio carried whole, its tests and its stream check with it, rather than trimmed to the plan's WAV and MP3 (that plan's entry above, "Audio formats"): its mixer decodes WAV, MP3, and Ogg Vorbis and plays streamed sounds through the same paths, so cutting Ogg and streaming out would have been surgery on tested code for no saving -- the web build carries no decoder either way, and a native build links libvorbis only with audio. The racing game's music will stream. So libwgf vendors libogg and libvorbis again (`deps/xiph`, BSD 3-Clause, back in THIRD_PARTY_NOTICES.md), and keeps the streamed sound's own handle kind (41, "audio.sound_streamed"); both kinds are `wgf_sound_t`. The audio-music example (its music streamed, a click, S stalling a frame for 300 ms) and the CC0 music and click it plays came with it. Every audio test ran and passed on every preset, the browser's included, and on sightblinder.

## Audio on a machine without a sound card (2026-10-05)

Step 5's CI run failed on Linux: GitHub's runner has no sound card, sokol_audio's setup found no device, and libwgt's mixer (carried) shut sokol_audio down only when a device was valid, so the next start in the same process asserted. It now shuts down whenever it set up, and `wgf_audio_sound_no_device_test` runs the sound test with ALSA given no configuration, so a machine with a sound card tests the case too.

## Milestone 1, step 6, ecs: closed (2026-10-05)

libwgt's ecs (flecs_wrapper-c's, carried into it) was a 3D one: scenes of glTF, a physics system, transform hierarchies in flecs, and a callback per system across its binding. libwgf's is written for what milestone 1 needs and SPEC's invariants, on the same flecs (v4.0.5, the distr amalgamation, unchanged).

- **flecs's core alone.** `FLECS_CUSTOM_BUILD` with no addons -- no script, no REST, no JSON, no pipeline or systems addon -- and its default OS API, compiled once (`wgf_ecs_flecs_impl.c`), warnings off for it alone. libwgf's systems are plain functions over cached queries, run by the ecs part's tick, so flecs's scheduler isn't needed; its tables and queries are what it is for. Queries are capped at 8 terms (`FLECS_TERM_COUNT_MAX`; libwgf's have 3): flecs sizes every query description for its maximum, and making the world nests several, which at 32 overflowed a web page's 64 KB stack when the first entity was made inside a frame (the browser check caught it; the ecs's tests are headless, so none runs on the web). With 8 it ran in a 32 KB stack, checked (`-sSTACK_OVERFLOW_CHECK=2`); the browser check of ecs-scene, which makes its world inside a frame, is what guards it. On the web it is the largest thing a program links: in wasm32-release, 303 KB of ecs-scene's 719 KB of code at -O3, so flecs alone is compiled for size (-Oz) in a web release, which halves it to 152 KB and takes ecs-scene from 287 KB to 237 KB gzipped (gfx-canvas is 145 KB); flecs's part of a tick is walking tables, and the systems' loops are libwgf's own, still -O3. Asteroids' size budget (step 11) is set with this in it.
- **The entity and node split.** Simulated state is flecs components, plain data; a node, a voice, names, and a behavior's parameters are in libwgf's record per handle. Drawing stays gfx's: an entity's node is a plain node it owns, and each visual component (shape, sprite, text, emitter) a node of that type under it, so a canvas draws entities with everything else, and nothing in gfx knows the ecs exists. Hierarchy is the nodes': an entity made under another's node goes when it does; the systems move each entity in its parent's space, and colliders compare only siblings, so no transform hierarchy is kept in flecs.
- **Ticks and frames.** The systems run at the tick rate; frames draw each entity between its last two ticks (the plan's fixed tick with interpolation). Wrapping shifts the kept position by the same span, so a wrapped rock is drawn moving on, not swept back across; `wgf_entity_snap` is for one put somewhere new. Core's part list gained a tick_begin, for keeping each transform as the tick starts, and the frame's tick fraction (`wgf_core_priv_part_set_fraction`), which app sets before the parts' updates.
- **Triggers, not physics.** A collider is a circle, a layer, and a mask; overlaps are found by sorting along x and sweeping, per parent node, and entered and exited by walking this tick's sorted pairs against the last's. Asteroids needs no more (ROADMAP, "Later": physics2d).
- **One async model.** What the systems raise -- a behavior's CREATED and DESTROYED, triggers entered and exited -- queues as triples of ints, taken in bulk by the program (`wgf_ecs_take_events`), so the binding dispatches a behavior's calls from a poll and no system calls into a script (SPEC: "Scripts set intent"). Behaviors are named, with text parameters from the scene, and found or counted by name in bulk.
- **Bulk calls.** Positions read and written for many entities in one call, through caller-owned arrays (SPEC's invariant); check_api's pairing rule names `wgf_entity_set_transform`'s getters.
- **Scenes as text.** A line-based format of its own (`wgf_scene.h`), not JSON or flecs script: it diffs and merges, it is parsed in a few hundred lines with every refusal a logged line number, and the dump writes it back, so a world dumped and loaded again dumps the same text (tested). Prefabs, with `from` for one built on another, are spawned at run time; a scene is a resource loaded through core's pipeline, parsed on a worker.
- **Tests**: entities and components with every refusal, the systems ticked as the runtime ticks them (motion, damping and top speed, each bounds mode, lifetimes, colliders by layer, mask, and parent, the probes, interpolation across a wrap), and scenes (loading, instantiating, spawning, every refusal, the dump's round trip). The ecs-scene example instantiates `examples/assets/scenes/field.scene` and spawns sparks from a prefab: the feature test's first scene, run headless, in a window, and in the browser by every check.
